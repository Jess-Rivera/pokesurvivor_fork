Refactor track: how to structure it proposed 2026-11-14

A side track that pays down the tangles from the three shape maps without touching feature work in progress. Small slices, each proven to change nothing, in their own folder and branch. Nothing here is approved yet; section 7 lists the decisions.

1. The shape: three lanes, two folders

mainalways playable
today→gym-leader-ai merges→R0 merges→R1 merges→R2 ...
feature/*pokesurvivor_fork/ · current work, either tool
#39→#30→review→merge·next feature merges main, picks up R slices
refactor/*pokesurvivor_refactor/ · a second folder
R0 safety net→R1→R2→...·one short branch per slice, cut from main

main

Only receives finished, proven slices. Both tracks start from it and merge back into it.

Feature folder

Unchanged: pokesurvivor_fork/, STATE.md, the board. Cleanups that touch its own files happen here as touched-code cleanups (like the leader-ai split before #39).

Refactor folder

A git worktree: same repo, second folder, its own branch. The two can never edit the same checkout, and one branch can't be checked out in both.

Shared handoff docs conflict on every mergeThe refactor track does not edit STATE, TODO, DEVLOG or the DECISIONS index. It keeps its own handoff in docs/branch-rules/refactor-track.md; one DEVLOG line is added when a slice merges (decision D2).
changelog.js conflictsBehavior-preserving slices add no patch note, or one line at merge (decision D3).
Long-lived branch drifts from mainOne branch per slice, merged within about a week. Merge main into it before starting each session.
Two tools on one branchOne owner per branch at a time. Switching tools: commit, push, pull on the other side (same as today).
Behavior sneaks in under "refactor"Every slice is behavior-preserving by default. Any change a player could notice is a standalone decision, never a line in a plan.

Size cap per slice

  • One tangle, about one session of work, two or three files.
  • A slice that grows past that is split: the extra part becomes the next slice's issue.

4a. The safety net (built first)

ToolWhat it proves

Ratchet counts in check.jsnumbers that may only go down: unseeded rolls in sim files, FX/Audio/animator calls in sim files, files over 1000 lines. Stops new spaghetti from either session once on main.

1. Manageable

One tangle per slice, one session each, a pinned harness before touching anything, merge and delete. The shape maps are the backlog.

2. Aside, safely

A second folder on its own branch, a no-touch list of the feature's files, and its own handoff file instead of STATE, TODO and DEVLOG.

3. Principles

Each plan fills in the rulebook's plan check, deletes before restructuring, and the ratchet counts keep new spaghetti from coming back.
