## Plan decisions (recommended; approved with this plan)
- P1 Routed list: add exactly psychic, confusion, bubble-beam, aura-sphere, rock-slide (33 routed in total after 4c-1 and 4c-2). The list stays in js/systems/move-route.js only. Flag off, the game is unchanged. Flamethrower is already routed; its behavior changes through P2.
- P2 aimTrack (D1, D2). For a caster-anchored static shape with aimTrack, the shape's heading turns each step toward the tracked enemy by at most aimTrack (rad/s) x dt, with the angle difference wrapped to the shortest way (the same convention and helper as turnRate, DECIDED Q13). Frame order: the shape follows the owner (R8), then the heading turns, then containment is tested at the new heading. Tracked target rule: the cast target while it is alive and within range; when it dies or leaves range, re-pick the nearest live enemy within range (ties: lowest id, no rng); this re-pick repeats whenever the tracked enemy is lost; with no enemy in range the heading holds. Unlike steering (D23), there is no "one re-pick only", because a static cone has no fly-straight fallback. The cast gate for nearest and a static caster shape is unchanged (R9: waits for the target within min(range, reach + target radius)). The initial heading is the cast aim, as today. The lens, growth and the 4b commitment (Flamethrower slowed plus freeze) are unaffected.
- P3 Flamethrower data and tests. No data change (aimTrack 1.4 is already there). Update every expectation in the 3d, 4a, 4b and smoke tests that assumes Flamethrower's cone never turns, and add the aimTrack cases in Tests. In the finish report tell Jess plainly that Flamethrower's feel changed (the cone now swings toward its target at 1.4 rad/s for its 1.0 s) so he can re-playtest it.
- P4 Location targeting (R9, F3). Add a `location` entry to the AIM table. With locationPick enemy (the resolver default): pick one live enemy within `range` using the sim's seeded rng (the same rng object the other rolls use, so a fixed tape stays deterministic; ties impossible, the pick is a uniform index over candidates sorted by id), the point is that enemy's position at cast time and does not track it afterward. With locationPick caster: the point is the owner's position (build both values since the grammar has both; the caster value is used by no routed move, test it with a synthetic move). The cast gate waits (retry every 0.05 s, cooldown not spent) while no candidate is within range, and it does not consume rng while waiting. castSlot carries the point onto the cast so spawnInstance's existing `cast.point` read for a world anchor works; the cast target for a location move is the picked enemy (informational). Do not touch the other AIM entries.
- P5 Delay (Q17, D28). An instance with `delivery.delay` waits before it exists physically: during the wait it has no motion, no collision, no hit records, no endOn evaluation, and its age stays 0; when the wait reaches 0 the instance activates, and endOn `time` counts from activation (so Rock Slide is active for exactly 0.2 s after a 0.4 s wait). A wait does not end early on owner death rules that normally end an instance unless they would anyway (ownerDeath and notActive still end it; time does not). The remaining wait is exposed on the instance (for the render) and nothing else reads it. A move without delay behaves exactly as before.
- P6 Falls (R8). Add `falls` to the MOTION table as a world-anchored motion that never moves by itself (R8: a world shape never moves unless its own motion says so): it sits at the cast point. If moveSpeed is present the validator allows it but the motion ignores it in this slice; report that to Jess, do not invent a drop motion in the sim. The falling look is render-only (P8). Rock Slide as built: a full circle of radius 70 (lens applies as for other circles) tested once per step over its 0.2 s active window, oncePerInstance (each enemy once), damage and the 4a flinch rider at 30 percent. Enemies can walk out of the circle during the 0.4 s wait; that is by design.
- P7 Routing and verification of the travelling moves (no sim change expected beyond P2 to P6). If routing exposes a gap in the existing travel code (grow on a travelling wedge, oscillate phase per shot, curve with a full fan, the Psychic re-pick), fix it inside move-sim.js and say so, and stop and tell Jess if it needs a new rule. Per architecture: Psychic apex moves with the instance, heading steers at most turnRate x dt toward the cast target then ONE re-pick of the nearest, radArc follows D21 and reaches 2.0 at t = 1.0 s, D18 containment each step with the apex rule, oncePerInstance. Bubble Beam: lateral offset = amplitude x sin(2 pi x frequency x t) exactly (D24), independent of dt. Aura Sphere: heading turns by curve x dt each step (D23), six shots 2 pi / 6 apart; record the measured reach in the harness (about 160 px expected) without changing data. Confusion: clamped homing at turnRate (D23), one roll at 10 percent through the 4a ailment applier.

Psychic's wedge drawn as a translucent growing wedge, Bubble Beam as small bubbles, Confusion as a small homing orb, Aura Sphere as spheres with a short trail, whichever the renderer already does for routed shapes.
