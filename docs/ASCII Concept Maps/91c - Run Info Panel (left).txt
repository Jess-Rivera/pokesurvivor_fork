DEBUG TOOLS FOR THE PANEL  [Approved]   js/core/debug.js, ?dev only, all English console output
=====================================================================
Why: under ?dev you play as a guest, whose save lives in memory only (db.js: guest saves are never stored).
A reload forgets everything, and any debug call flags the run, which (D5) never sets a record. So a record
can never be seen the natural way in a dev session. These tools seed and inspect instead.

 G.Debug.runinfo(preset)        seed THIS run's counters so every Run Info row has something to show
   'full'   every section filled, tall enough to SCROLL: kills, elites, splits for 3 gyms, faints spread over
            the team (one Pokemon clearly "most"), every status kind landed, DoT, taken / healed, items,
            shinies seen 2 caught 1, biggest hit, EVs. Per-Pokemon parts are seeded too (they must add up).
   'empty'  a fresh run: Faints 0 with its sub-lines hidden, Statuses "None yet", no splits
   'tie'    'full', but two Pokemon tie on Most faints (the lower slot must show)
   no arg   logs the run's counters as a table (team totals and per Pokemon)
   Flags the run (like every debug call). Opens nothing: pause to look.

 G.Debug.regionbest(arg)        the region record on the current save (in memory for a guest)
   no arg            logs this region's record, or "No record yet"
   { loop, gyms, time }   sets it, e.g. { loop: 1, gyms: 3, time: 1120 } (seconds), plus its gym splits
   'clear'           removes this region's record (the empty state)
   'old'             removes the WHOLE save field, as an old save has it (tests the default path)

 G.Debug.recordcheck(write)     runs the real end-of-run compare on THIS run, as if it ended now
   no arg            dry run: logs "would be a new best" or "not better", and WHY (loop, gyms, then time),
                     and that a normal run end would refuse it because the run is flagged. Writes nothing.
   'write'           writes it anyway, so a following pause or run shows the new record  (T1, a dev bypass)

 WHAT A ONE-SESSION TEST LOOKS LIKE (no reload, so the guest save keeps it)
   1  dev.html?dev, start a run, G.Debug.runinfo('empty'), pause        -> "No record yet", "None yet"
   2  G.Debug.runinfo('full'), pause                                    -> every row, panel scrolls,
                                                                           header stays, reopens at top
   3  G.Debug.runinfo('tie'), pause                                     -> Most faints = lower slot
   4  G.Debug.regionbest({ loop: 1, gyms: 2, time: 900 }), pause        -> Region Best shows it,
                                                                           "This run" ahead / behind
   5  G.Debug.recordcheck()                 -> dry-run verdict and reason in the console
   6  G.Debug.recordcheck('write'), End Run, new run, pause            -> the record carried over
   7  G.Debug.regionbest('old'), pause                                  -> "No record yet", no error

 DECISIONS
   T1 recordcheck('write') writes a record from a flagged run. That bypasses D5's "flagged never sets a
      record", but ONLY through this explicit dev call; a normal run end still refuses. <- rec (dry run
      by default).  Alternative: no write at all, set records only with regionbest().
   T2 names: runinfo / regionbest / recordcheck, lowercase like the other debug calls (evbank, runslots) <- rec

 TESTS FOR THE TOOLS
   smoke-pause-menu.js seeds through these same calls (so the tools are exercised every smoke run):
     runinfo('empty') then 'full' then 'tie' checks as in the panel's smoke list above; regionbest({..})
     shows the record; regionbest('clear') and ('old') show "No record yet" with no page error;
     recordcheck() writes nothing; recordcheck('write') writes and a new run's pause shows it.
   run-stats-harness.js: the compare that recordcheck calls is the same function the harness tests
     (one compare, not a debug copy), checked by a harness line that both paths give the same verdict.
   debug.js header comment: the three calls listed with the others.
   Debug set for feel testing: the 7-step session above.
